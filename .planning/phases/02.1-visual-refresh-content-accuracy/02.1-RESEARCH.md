# Phase 02.1: Visual Refresh & Content Accuracy - Research

**Researched:** 2026-02-13
**Domain:** CSS-first design system transformation, static asset migration, technical content verification
**Confidence:** HIGH

## Summary

This phase involves three distinct domains: (1) transforming the current dark industrial design system into a light professional palette using Tailwind CSS 4's @theme directive with OKLCH colors, (2) integrating legacy product images from the www/ directory plus stock photography using Astro's built-in Image component, and (3) auditing all technical claims in the i18n files to ensure factual accuracy and proper attribution to Czech certifications.

The project currently uses a dark color palette defined in src/styles/global.css via @theme with OKLCH colors (surface-900 through surface-50, accent colors at 250 hue). All 21 component files reference these design tokens using bg-surface-*, text-*, and border-* utilities. The transformation requires updating @theme variables while maintaining the existing utility class names to avoid changing component code.

Legacy images exist in www/domu_htm_files/ (169 total files including product photos and certificate scans like "2Certifikat vyrobku cz.jpg"). Astro 5.17.0 with Sharp (configured in package.json) provides automatic WebP/AVIF optimization and responsive srcset generation for images in src/. The www/ directory requires migration to public/ or src/assets/ for processing.

Content audit reveals critical technical claims across 271 i18n keys: thermal conductivity (0.001 W/m·°C), temperature range (-60°C to +260°C), fire classification (ČSN EN 13501-1 class E), and elongation (80%). These require verification against actual certificates and test protocols mentioned in the certificates page.

**Primary recommendation:** Update @theme colors using perceptually uniform OKLCH values for light mode, migrate legacy images to src/assets/ with Astro Image component for optimization, and create a verification checklist to cross-reference all technical claims against source documents.

### Pattern 1: CSS-First Theme Transformation (Light Palette)

**What:** Update @theme variables in global.css to light OKLCH values while preserving utility class names.

**When to use:** When changing color palette without modifying component code (21 Astro files use bg-surface-*, text-*, border-* classes).

**Example:**
```css
/* src/styles/global.css - BEFORE (Dark Industrial) */
@theme {
	--color-surface-900: oklch(0.15 0.01 250);  /* Dark background */
	--color-surface-800: oklch(0.2 0.01 250);
	--color-text-primary: oklch(0.95 0.005 250); /* Light text on dark */
}

/* AFTER (Light Professional) */
@theme {
	--color-surface-900: oklch(0.98 0 0);       /* Near-white background */
	--color-surface-800: oklch(0.94 0 0);       /* Subtle gray */
	--color-text-primary: oklch(0.15 0.01 250); /* Dark text on light */

	/* Invert semantic meaning: surface-900 becomes lightest, surface-50 becomes darkest */
	/* OR remap components: change bg-surface-900 → bg-surface-50 in BaseLayout.astro */
}
```
**Source:** [Tailwind CSS Theme Variables Docs](https://tailwindcss.com/docs/theme)

**Decision point:** Option A: Invert variable values (surface-900=light, surface-50=dark) - no component changes. Option B: Keep variable meanings and update all component classes (21 files). **Recommendation:** Option A for speed.

### Pattern 4: Technical Claims Verification Checklist

**What:** Systematically verify each technical claim against source documents (certificates, test reports) or authoritative references.

**When to use:** For all numerical specifications, certification claims, test results in i18n files.

**Verification matrix:**
| Claim Type | Source Required | Verification Method | Confidence Level |
|------------|----------------|---------------------|------------------|
| Test results (0.001 W/m·°C) | Test protocol PDF | Exact number match | HIGH if matches |
| Certification (ČSN EN 13501-1) | Certificate document | Standard number + classification | HIGH if matches |
| Temperature range (-60 to +260°C) | Product certificate | Range match + conditions | HIGH if documented |
| Performance claims ("1mm = 50mm") | Calculation from test data | Derived value validation | MEDIUM - needs formula |

**Process:**
1. Extract all technical claims from cs.json and en.json
2. Locate source document (www/ or request from client)
3. Cross-reference claim to source
4. Mark discrepancies for client review
5. Update i18n files with verified values

**Source:** [Guide to Fact-Checking and Information Verification](https://data.misa.org/api/files/1714981306287l58ejryzrcj.pdf)

### Anti-Patterns to Avoid

- **Anti-pattern:** Defining light colors in :root instead of @theme → Utilities won't be generated, must use arbitrary values [bg-[color]]
- **Anti-pattern:** Placing legacy images in public/ → No optimization, no srcset, no format conversion
- **Anti-pattern:** Using remote URLs for stock photos → External dependency, no optimization, slower loading
- **Anti-pattern:** Changing technical claims without source verification → Legal risk, customer trust damage
- **Anti-pattern:** Using low-chroma OKLCH for accent colors in light mode → Washed out appearance, poor contrast

## Common Pitfalls

### Pitfall 1: OKLCH Lightness Confusion in Theme Inversion

**What goes wrong:** Inverting from dark to light mode by swapping lightness values (0.15 ↔ 0.98) without considering semantic token usage. Components expecting surface-900 to be "darkest background" break when it becomes "lightest background".

**Why it happens:** Design tokens have semantic meaning encoded in their names (900=darkest, 50=lightest in typical systems). Inverting values without renaming creates cognitive mismatch.

**How to avoid:**
- **Option A (Fast):** Flip the semantic meaning - document that surface-900 is now lightest in light mode. Update global comment in @theme block.
- **Option B (Correct):** Search-replace all bg-surface-900 → bg-surface-50 across 21 component files to maintain semantics.

**Warning signs:** Header/footer backgrounds appear white when expecting dark, text becomes invisible due to white-on-white.

**Recommendation:** Option A for this phase (speed), add TODO for Phase 2.2 cleanup if design tokens need to follow Tailwind conventions.

### Pitfall 2: Legacy Image Format Assumptions

**What goes wrong:** Legacy www/ images with .png extension are actually JPEGs (or vice versa), causing format detection errors or poor optimization.

**Why it happens:** Xara Web Designer 9 (detected in EXIF metadata of 185.jpg) may have exported with non-standard extensions.

**How to avoid:**
1. Run `file` command on all legacy images before migration
2. Verify format matches extension
3. Rename if necessary (185.jpg.png → 185.jpg)

**Warning signs:** Astro build errors like "Could not determine image format", unexpectedly large output files.

**Current status:** Checked sample files - formats match extensions (155.jpg=JPEG, 122.png=PNG). But verify ALL 169 files before batch migration.

### Pitfall 3: Thermal Conductivity Measurement Validity

**What goes wrong:** Claiming 0.001 W/m·°C thermal conductivity without understanding test method limitations.

**Why it happens:** Research reveals standard heat flow meters cannot measure values below 0.01 W/m·K with acceptable accuracy. Values as low as 0.001 W/m·K require specialized steady-state comparative methods.

**How to avoid:**
- Locate the actual test protocol (certificates.test.test01.description references this measurement)
- Verify test method used (ISO 8301? ASTM C518? Custom apparatus?)
- Check if certificate specifies measurement uncertainty
- If protocol unavailable, flag claim as **NEEDS VERIFICATION** for client

**Warning signs:** Certificate shows different value, test method inappropriate for material thickness, no measurement uncertainty stated.

**Critical note:** Research found that liquid nano-ceramic coatings show high variability in published values (0.001-0.14 W/m·K) depending on test method. [Laboratory Tests with Liquid Nano-ceramic Thermal Insulation Coating](https://www.sciencedirect.com/science/article/pii/S1877705815031604) warns of measurement challenges.

**Status:** Test protocol not yet reviewed - **MUST VERIFY before publishing**.

### Pitfall 4: Fire Classification Misinterpretation

**What goes wrong:** Claiming material is "non-combustible" when ČSN EN 13501-1 Class E means "no performance determined / highly combustible".

**Why it happens:** Class E is the second-lowest rating (only F is worse). Only A1/A1fl/A1L are truly non-combustible per standard.

**How to avoid:**
- Current i18n claims: "Nehořlavý" (non-combustible) and "třída reakce na oheň E" (Class E reaction to fire)
- **These are CONTRADICTORY** - Class E is NOT non-combustible
- Verify actual certificate classification
- Update language to match: "Class E - does not spread flame" is accurate, "non-combustible" is NOT accurate for Class E

**Warning signs:** Certificate shows Class E but marketing claims "non-combustible" or "fireproof".

**Current status:** cs.json line 172 contains contradictory claim - **MUST FIX**.

**Source:** [EN 13501-1 Fire Classification Performance Classes](https://measurlabs.com/blog/en-13501-1-fire-classification-performance-classes-and-criteria/)

### Pitfall 5: Image Migration Breaking Existing References

**What goes wrong:** Moving images from www/ to src/assets/ breaks references if old site URLs are hardcoded anywhere.

**Why it happens:** Legacy site may have been publicly accessible, old URLs may be cached or linked externally.

**How to avoid:**
- Check for hardcoded image paths in i18n files, components
- Add redirects in _redirects file for Cloudflare Pages if needed
- Don't delete www/ directory until verifying no external references

**Warning signs:** 404 errors in browser console, broken image icons on deployed site.

**Current status:** No hardcoded image paths detected in grep of src/ - safe to migrate.
